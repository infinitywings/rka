# v2.6.3 → v2.7.0: The Tool-Surface Arc

**Status**: canonical narrative — companion to `CHANGELOG.md`.
**Scope**: MCP layer only. The service layer, REST API, DB schema, and
Pydantic domain models are unchanged across the entire arc.
**Last updated**: 2026-06-02 (v2.7.0 GA shipped at commit `049a6dd` on
`main`; absorbed into `agentic` at `0032641`).

This document is the single end-to-end account of the empirical
investigation that began on 2026-06-01 with a PI cockpit unable to call
`rka_add_literature` despite the tool being on the wire, and ended on
2026-06-02 with a no-compromise discriminated-union dispatch surface
that makes structural correctness inevitable at the inputSchema layer.

Read `CHANGELOG.md` for the per-release semver entries (they are the
system of record). Read this document for the connective tissue: why
each release shipped, what we measured, what we learned about Claude
Desktop's behavior, and why the v2.7.0 architecture is the
only sustainable place to land.

---

## Problem statement

RKA's MCP server had grown to 91 tools by mid-May 2026. The 91 number
itself was not the problem — domain coverage genuinely required that
many distinct operations. The problem was that **Claude Desktop's
client-side tool-selection filter** silently dropped tools the LLM
could not see, even though the server had handed them across the
wire.

On 2026-06-01 (the hyperscaler-auditing mission), the PI tried to
call `rka_add_literature` to import a paper. The tool existed on the
server. The `tools/list` response contained it. The LLM never offered
it. Investigation of `mcp-server-rka.log` confirmed Claude Desktop
delivered the full 91-tool list to its client process, then surfaced
only 7 to the LLM (the most-recently-used and most-semantically-
relevant per turn). The LLM had no mechanism to ask for more, so the
cockpit could not progress until the PI hand-edited claude_desktop_
config.json to remove unrelated MCP servers and restart.

This is **Retrieval-Augmented Tool Selection (RATS)**: Claude Desktop
embeds the user's turn, ranks every registered tool by relevance, and
surfaces the top-N (empirically 7–30 for `rka` depending on prompt
context, with a hard ~100 ceiling across all servers combined).
Anthropic does not document RATS publicly; its existence has to be
inferred from the wire logs and the cockpit's observed behavior.

Three failed approaches followed before we found the correct shape.
Each one was a load-bearing experiment whose negative result narrowed
the design space:

1. **Navigator pattern** (v2.6.3) — keep a small set of high-leverage
   tools always-on; ship a `rka_load_tools` meta-tool that registers
   deferred tools on demand via the standard MCP
   `notifications/tools/list_changed` mechanism. Failure mode:
   Claude Desktop *does not honor the notification reliably*, and
   the navigator itself can be filtered out by RATS, leaving the
   cockpit with zero discoverability.

2. **Intent verbs** (v2.7.0a1) — collapse 91 named tools into 8
   intent-grouped verbs (`rka_query`, `rka_record_decision`, …). Each
   verb takes a discriminator (`scope`, `action`, `target`) and routes
   to the existing REST endpoints. Failure mode: when the user's
   prompt vocabulary semantically matches a legacy tool name better
   than the verb's trigger phrases, RATS picks the legacy tool. With
   91 legacy + 8 verbs all visible, the relevance race is unfair.

3. **alwaysLoad hint** (v2.7.0a2) — set
   `_meta["anthropic/alwaysLoad"]: true` on the 20 always-on tools.
   Anthropic docs at `code.claude.com/docs/en/mcp` advertise this as
   the supported mechanism to bypass per-turn ToolSearch. Failure
   mode: the hint is documented as **Claude-Code-only**. Claude
   Desktop ignores it entirely — empirically confirmed via wire-log
   inspection plus three unfixed GitHub bugs against Claude Desktop's
   broken `tool_search` handling (#25892, #41472, #49073).

The pre-mortem of a fourth approach — `rka_execute(operation, **kw)`
with `**kw` as a free-form dict — surfaced four high-severity
compromises (see *The pre-mortem's 4 compromises* below). The PI
explicitly chose to pay the full implementation cost of a typed
discriminated union over accepting any of those compromises. That
choice produced v2.7.0 GA.

## What we learned about the environment

The arc's most durable output is the corrected mental model of how
the Anthropic clients surface tools. These findings are framework-
relevant and worth carrying into any future MCP server design.

### Claude Desktop's `tool_search` is empirically broken

Three unfixed GitHub bugs corroborate the cockpit's observation:
- **anthropics/claude-code#25892** — tool search results don't include
  all registered tools
- **anthropics/claude-code#41472** — tool search ranking ignores
  description content under certain prompt shapes
- **anthropics/claude-code#49073** — `_meta` hints not respected by
  Desktop client even when server surfaces them

All three were filed against versions current as of 2026-05 and
closed-without-fix. The cockpit-observable surface filter ranks tools
by an opaque combination of:
- Semantic similarity between user turn and tool name + description
- Recent call history (the tool-was-just-used heuristic)
- Per-server cardinality (likely a soft cap)
- Cross-server priority among connected MCP servers

The filter is *not* dependent on the server-instruction string
(`RKA_INSTRUCTIONS` cannot influence which tools surface).

### `alwaysLoad` is Claude-Code-only

`code.claude.com/docs/en/mcp` documents
`_meta["anthropic/alwaysLoad"]: true` as the supported hint to
bypass ToolSearch. The hint is honored by **Claude Code** (the IDE-
hosted Claude that runs `claude-agent-sdk`) but **not by Claude
Desktop** (the consumer chat app). This is not advertised on the
public docs page; we inferred it from v2.7.0a2's empirical no-op.

For RKA this means the orchestrator's daemon subprocess (which is
a `claude-agent-sdk` instance, so Claude-Code-like) benefits from
`alwaysLoad`, but the PI cockpit (Claude Desktop) does not. The
v2.7.0 GA design accommodates this by shipping a 5-tool always-on
surface that's small enough to always survive RATS regardless of
which client.

### The 30–50 quality knee and ~100 hard cap

Empirically, cockpit tool-selection accuracy degrades around 30–50
visible tools per server and the LLM appears to stop seeing tools
entirely past ~100 across all servers combined. RKA's 91-tool surface
sat squarely in the degradation zone. The 5-tool v2.7.0 surface sits
comfortably below the knee.

### `notifications/tools/list_changed` is not honored by Claude Desktop

The MCP protocol specifies that servers can emit
`notifications/tools/list_changed` to inform clients that the
registered tool set has changed; clients SHOULD re-fetch. Claude
Code honors this. Claude Desktop does not, empirically — v2.6.3's
navigator pattern was designed around the assumption that it would,
and that assumption falsified within the first cockpit test.

### Industry precedent: intent-grouped thin surfaces

Two production examples ship the intent-verb shape that v2.7.0 ended
on:
- **Cloudflare**: 2,500+ API endpoints exposed via 2 MCP tools.
  Documented in their MCP server's README; surfaces cleanly on both
  Claude Code and Claude Desktop.
- **Awkoy `notion-mcp`**: 36 Notion API endpoints collapsed to 2
  tools. Explicit Claude Desktop support is called out. Pattern
  matches our `rka_query` + `rka_execute` shape.

Cloudflare and Awkoy use **untyped `**kw`** for the per-operation
body. v2.7.0 uses a **typed discriminated union**. This is the
difference the pre-mortem identified — the typed shape closes
compromises that the untyped shape leaves open.

## The pre-mortem's 4 compromises

The pre-mortem (workflow `wv5y9n0jt`) imagined a candidate v2.7.0a3
shape:

```python
@mcp.tool()
def rka_execute(operation: str, **kw: Any) -> str: ...
```

Four high-severity compromises surfaced. Each one was load-bearing;
the discriminated-union refactor closes each at the schema layer.

### Compromise 1: Enum regression (HIGH)

**Mechanism**: `**kw: Any` forces every field validation to runtime.
The Phase-X² work earlier in 2026-06 had hardened RKA against
`confidence='confirmed'` hallucinations (the LLM picking a plausible-
sounding value not in the canonical set) at three layers: server-side
Pydantic, orchestrator `TOOL_ARG_ENUMS` validator, and
LLM-emission-time `Annotated[Literal[...]]` inputSchema enum. The
inputSchema enum is the load-bearing layer — it makes the wrong
value impossible to emit, not just rejected after emission. An
untyped `**kw` collapses that layer entirely. The LLM regains the
ability to hallucinate `confidence='confirmed'` and discover the
error only after a wasted round-trip.

**Closure at schema layer (v2.7.0)**: FastMCP renders
`Annotated[Union[RecordNoteArgs, ..., ExtractClaimsArgs],
Field(discriminator='operation')]` as `inputSchema.oneOf` with
per-branch enum constraints on every Literal field. Each branch's
required-array surfaces the right fields. The LLM sees the canonical
value set BEFORE emitting; the Pydantic validation that backs
`Annotated[Literal[...]]` enforces it on the way through. Empirical
proof: 6/6 hallucination test cases raise `pydantic.ValidationError`
in `test_v270_typed_args_vs_models.py` (workflow `wdug5yr8t`).

### Compromise 2: Provenance inputSchema visibility (MEDIUM)

**Mechanism**: `**kw: Any` cannot express `related_journal:
list[str] = Field(min_length=1)`. The Brain LLM's only signal that
a decision requires non-empty journal provenance would be the
docstring — and docstrings are stripped from many tool-picker
surfaces. v2.6's project_id discipline was preserved by an HTTP
header; provenance discipline cannot be hidden in a header because
the field has variable cardinality.

**Closure at schema layer (v2.7.0)**:
`RecordDecisionArgs.related_journal` is `Field(min_length=1)` on a
typed Pydantic model. FastMCP renders the constraint into the
`oneOf` branch's `required` array AND emits a `minItems: 1`
constraint on the field's schema. The LLM sees the requirement at
emission time, not after a wasted token spend.

### Compromise 3: Discoverability cost (HIGH)

**Mechanism**: with `**kw: Any`, the LLM has to consult
`rka_describe(operation)` to learn each operation's signature.
The original v2.7.0a3 design's `rka_describe('')` index returned
6,563 tokens — a full inventory of operation summaries. Every fresh
cockpit session that needed to discover the right operation paid
that token cost before any work happened.

**Closure at schema layer (v2.7.0)**: `rka_describe('')` returns
<250 tokens — a one-line summary per operation pointing the LLM to
the per-branch schema, which is already in the `inputSchema.oneOf`
the LLM has from `tools/list`. The describe roundtrip becomes
optional, not load-bearing. Verified in workflow `w058g0juk` test
output.

### Compromise 4: Orchestrator autonomy-contract collapse (HIGH)

**Mechanism**: the orchestrator's TWO-TAP autonomy gate at
`pi_decision_select` is per-tool-granular. Brain proposes a set of
`(tool_name, args)` actions; PI ratifies with `accept` or `correct`;
parent-side `execute_ratified_actions` dispatches each one through
`WRITE_TOOLS` allowlist + `TOOL_ARG_ENUMS` validator. The autonomy
contract reads: *"PI explicitly approved tool X to be called with
args Y."* If the LLM-facing tool becomes `rka_execute` for all 49
write operations, the allowlist becomes one entry and the ratification
text reads *"PI approved rka_execute with args"*, which collapses the
gate's semantic precision. The PI cannot ratify per-operation.

**Closure via env flag (v2.7.0)**: `RKA_LEGACY_TOOLS=1` environment
variable, read at MCP server startup, keeps the 91 legacy tools +
8 v2.7.0a2 verbs at `tier='always_on'` and demotes the 3 dispatch
tools to deferred. The orchestrator daemon's docker-compose.yml will
set this env (planned for v2.7.0+agentic.X release) so the SDK
subprocess sees the v2.7.0a2 20-tool surface and the TWO-TAP gate's
per-tool granularity is preserved. The PI cockpit sees the 5-tool
typed dispatch surface. **Two compatible surfaces, one binary.**

## The v2.7.0 architecture

### Always-on tools (5)

| Tool | Type | Operations |
|---|---|---|
| `rka_query(args)` | Discriminated union read | 38 read operations: status, context, journal, decisions, missions, literature, reports, claims, clusters, research-map, decision-tree, ego-graph, multi-hop, traces, etc. |
| `rka_execute(args)` | Discriminated union write | 49 write/lifecycle operations: notes, decisions, missions, checkpoints, reports, literature add/update/import, claim extraction, cluster mgmt, hooks, maintenance, etc. |
| `rka_describe(operation)` | Schema lookup | Returns the per-operation signature + example + related operations. `rka_describe('')` returns the <250-token index. |
| `rka_load_tools(names)` | Escape hatch | Brings deferred legacy tools online for backwards-compat callers. |
| `rka_help(topic)` | Escape hatch | Deprecated alias for `rka_describe`. Kept always-on so cockpits that already learned the v2.6.3 navigator vocabulary still get a working surface. |

### Typed Pydantic models (87)

`rka/mcp/operation_args.py` (3,687 LOC) contains 87 hand-curated
Pydantic models. Each:
- Inherits from `ProjectScopedArgs` (most) or `UnscopedArgs` (the
  session-shaped few like `list_projects`, `digest`, `health`).
- Has `operation: Literal['<name>'] = '<name>'` as its discriminator.
- Has each enum field declared as
  `Annotated[Literal[<canonical set>], Field(description=...)]`
  via the canonical aliases in `rka/mcp/_enums.py` (20+ Literal
  aliases: `ConfidenceLit`, `ImportanceLit`, `SourceLit`, etc.).
- Has `model_config = ConfigDict(extra='forbid', use_enum_values=True)`
  so unknown fields are rejected and enum values render as strings.
- Has `@model_validator(mode='after')` for cross-cutting invariants
  (16 validators in total — e.g. `source='pi'` requires
  `verbatim_input`; `related_journal` non-empty on
  `RecordDecisionArgs`; mode-exclusivity on
  `RecordLiteratureArgs`).

The model lookup surface is `OPERATIONS_SCHEMA` in
`rka/mcp/operations_schema.py` (2,874 LOC), a hand-curated dict
keyed by operation name with: tool, category, role_tag, summary,
signature, required_fields, optional_fields, enums, 1–2 examples,
related_operations, and Phase-X²' canonical-field-name reminders.

### Dispatch routing

`rka/mcp/verb_dispatch.py` adds `dispatch_query_typed(args)` and
`dispatch_execute_typed(args)` that receive typed model instances
and route via `isinstance` / `args.operation` to the same REST
endpoints the legacy tools hit. **The service layer, REST routes,
and DB schema are unchanged.** v2.7.0 is purely an MCP-layer
redesign. Parity is automatic and asserted by
`test_v270_legacy_parity.py` (parametrized byte-identical REST
payload comparison).

### Bookkeeper invariant

`git diff main -- rka/` is nonzero on the v2.7.0 commit because
this *is* a main-side release. `agentic` absorbs via the standard
`git merge origin/main` discipline. After merge (commit `0032641`
on agentic): `git diff main -- rka/` returns 0 again. The
orchestrator subtree (`orchestrator/`) is untouched in v2.7.0 GA;
the `v2.7.0+agentic.X` release will set the `RKA_LEGACY_TOOLS=1`
env in `orchestrator/docker-compose.yml` and rewrite the Brain /
Executor system prompts to teach the v2.7.0a2 verb shape.

## Empirical validation (PI cockpit session 2026-06-02)

After v2.7.0 GA shipped, the PI ran the following test in a fresh
Claude Desktop conversation:

> *"Bank this PI directive as source=pi: 'go ahead and ship.'"*

This is a deliberately ambiguous instruction. The empirical questions:

1. Does the cockpit pick the right operation?
2. Does the cockpit catch the historical `confidence='confirmed'`
   hallucination class without a wasted round-trip?
3. Does the cockpit refuse to act on ambiguity rather than guess?

Observed behavior:

1. Cockpit picked `rka_execute(operation='record_note', ...)`.
2. Cockpit attempted to set `confidence='confirmed'`, **caught it
   itself before emitting**, and quoted the allowed set verbatim
   from the inputSchema branch (`['low', 'medium', 'high',
   'verified']`). No round-trip wasted. **This is the
   no-compromise empirical proof** that the schema layer surfaces
   the constraint at the right moment.
3. Cockpit refused to act on "go ahead and ship" verbatim. Surfaced
   two possible readings — *(a) ship the v2.7.0 binary, (b) approve
   the next manuscript draft* — and asked the PI to pick. After
   disambiguation, the directive was banked as
   `jrn_01KT5N3RDW16633AW30CVF022T` (source=pi, verbatim_input
   preserved exactly, confidence=verified).

The cockpit went from *"discover-then-fail-then-retry"* to
*"discover-and-be-right-first-time"*. The schema layer makes the
class of error structurally impossible.

## Residual judgment calls (correctly left to the agent layer)

The v2.7.0 schema layer eliminates **structural** error classes.
Two error classes remain on the agent layer:

### Semantic mapping under ambiguity

When the user says "confirmed", the LLM has to map that token to one
of `low | medium | high | verified`. The schema rejects `'confirmed'`
but doesn't tell the LLM which legal value to pick. The cockpit's
choice (`verified` is the closest semantic neighbor for "confirmed",
or `high` if there's measurable uncertainty) is a judgment call.

The fix is **prompt engineering** (richer enum descriptions, worked
examples in BRAIN_SYSTEM / EXECUTOR_SYSTEM) — not a schema change.
The schema's job is to enforce the canonical set; the agent's job
is to pick within it.

### Context-bound routing

When the PI says "bank this directive in our hyperscaler project",
the LLM has to infer `project_id='prj_01KSMW9RBFXRY6HRRADH3SX7ZP'`
from the prose. The schema rejects calls missing `project_id` but
doesn't infer the right value.

The fix is **session priming** (state the project_id at the start
of every conversation; the LLM threads it through every subsequent
call). v2.7.0 cannot eliminate this; it can only ensure the LLM
fails loudly when it forgets.

These residuals are deliberate. The schema layer should not try to
solve them — solving them at the schema layer leaks agent-layer
judgment into the protocol and creates the next class of empirically-
surprising failure modes. The arc's discipline is: **enforce what
can be enforced structurally; surface what cannot.**

## Migration notes for v2.8.0

### When to fully drop the legacy 91 tools

Criterion: telemetry confirms **<5% per week call rate** on the
legacy tools for **3 consecutive weeks** before removing them. The
telemetry surface is the orchestrator workflow_runs cache plus
direct cockpit usage logs.

The `RKA_LEGACY_TOOLS=1` env flag survives v2.8.0 until that
threshold is met. Once removed, the orchestrator daemon must have
its prompts rewritten to use the v2.7.0 dispatch surface — see
the v2.7.0+agentic.X follow-up below.

### Orchestrator-side prompt rewrites (v2.7.0+agentic.X)

Planned but not yet shipped. The orchestrator's
`BRAIN_SYSTEM` and `EXECUTOR_SYSTEM` prompts currently teach the
v2.7.0a2 verb surface (8 intent verbs + 91 legacy). After
v2.7.0+agentic.X they will teach the v2.7.0 dispatch surface
(`rka_query` / `rka_execute` / `rka_describe`) for the daemon
subprocess. The `pi_decision_select` ratification text will need
to render per-operation rather than per-tool — the autonomy
contract is preserved at the operation granularity, which is
finer than the v2.7.0a2 tool granularity, so this is a refinement
not a regression.

`WRITE_TOOLS` allowlist will shrink from 9 entries to 1
(`rka_execute`), with the per-operation guard moving into
`TOOL_ARG_ENUMS` / new `OPERATION_ALLOWLIST`. The `execute_
ratified_actions` dispatcher will switch from `tool_name`
allowlist matching to `(tool_name, operation)` tuple matching.

Until v2.7.0+agentic.X ships, the daemon runs with
`RKA_LEGACY_TOOLS=1` and is byte-identical to the v2.7.0a2
surface it was integration-tested against.

### Service layer / REST / DB schema

Unchanged. v2.7.0 is purely an MCP-layer redesign. v2.8.0 will not
change them either; the dispatch tools call the same REST
endpoints the legacy tools hit. Parity has been the design
discipline throughout the arc and is asserted by
`test_v270_legacy_parity.py`.

## Anti-recommendations (what NOT to retry)

Per the deep-research workflow's findings, these approaches have
been empirically falsified or theoretically ruled out. Do not
re-attempt them without new evidence:

1. **Do not** ship a small navigator-only surface and assume the
   client will call the navigator on first turn. The v2.6.5
   experiment (3 always-on, 0 visible) is the falsifying data
   point. Claude Desktop's filter does not bootstrap from zero
   usage history.

2. **Do not** rely on `notifications/tools/list_changed` to surface
   newly-registered tools on Claude Desktop. The notification is
   part of the MCP spec but the client honors it inconsistently.
   The v2.6.3 navigator's whole runtime-expansion model rests on
   this and is brittle as a result.

3. **Do not** rely on `_meta["anthropic/alwaysLoad"]: true` for
   Claude Desktop cockpit work. It is documented as Claude-Code-
   only (`code.claude.com/docs/en/mcp`). v2.7.0a2 verified
   empirically. Use it for the orchestrator subprocess (which
   *is* a Claude-Code-equivalent), not for cockpit-targeted
   surfaces.

4. **Do not** ship an untyped `rka_execute(operation, **kw)` shape.
   The 4 compromises the pre-mortem surfaced are real and
   load-bearing. Cloudflare and Awkoy ship the untyped shape and
   accept the compromises; RKA has structural correctness
   requirements (provenance, autonomy contract, enum enforcement)
   that the untyped shape collapses.

5. **Do not** assume RATS reads instruction strings. v2.6.4 swept
   `RKA_INSTRUCTIONS`, `brain_orientation`, `executor_orientation`,
   README, USAGE_GUIDE, and the role SKILL.md files. The cockpit
   behavior was unchanged. RATS embeds tool names + descriptions,
   not server-side prose.

6. **Do not** expand verb descriptions past ~500 chars to game RATS
   ranking. v2.7.0a2 grew the `rka_query` description to 1,139
   chars in an attempt to capture T2 vocabulary. The cockpit
   behavior didn't improve in proportion to the description bloat.
   Anthropic's documented description guideline is ≤500 chars for
   a reason: longer descriptions dilute the embedding signal.

7. **Do not** put role-relevance information in description
   prefixes (the `[BRAIN]`/`[EXECUTOR]`/`[PI]`/`[ANY]` tag from
   v2.7.0a1's C-graft). The cockpit doesn't see role tags as
   relevance signal; it sees them as noise. v2.7.0 retains them
   for documentation but doesn't depend on them for surfacing.

8. **Do not** assume cross-server tool priority is per-server. The
   ~100 hard cap is across all connected MCP servers combined; if
   the PI's claude_desktop_config.json has zotero + orchestrator
   + Desktop Commander + rka, the rka surface competes with the
   others. Recommend in user-facing docs that the PI's config
   include only the servers needed for the current session.

The arc's central engineering lesson is: **empirical disciplines on
client-side opaque behaviors must inform the server-side design**.
We spent v2.6.3 → v2.7.0a2 trying to make the server-side fit the
client-side filter's assumptions. We landed v2.7.0 by accepting that
the filter's assumptions cannot be reverse-engineered reliably, so
the design must instead present a surface that survives any
plausible filter behavior. Five always-on tools, including three
typed dispatch tools that carry their full constraint surface in
`inputSchema`, achieves that.
